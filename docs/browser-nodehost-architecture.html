Web Researcher Browser Architecture

This document captures the browser path that is now working for the Web Browser Researcher agent. The key design is that the agent does not rely on a local desktop browser inside its OpenShift pod. It uses OpenClaw's supported node host browser proxy pattern and routes browser actions to a Fedora VM.

Agent Web Browser Researcher
Browser Runtime Chromium on Fedora VM
Control Pattern OpenClaw Node Host
Current Result Open, tabs, and browser session working

Executive Summary

The working path is: Agent Office UI or Discord message -> Web Researcher agent gateway in OpenShift -> paired OpenClaw node host on the Fedora VM -> managed headless Chromium profile named openclaw.

That matters because OpenClaw expects remote and container-based browser use to go through a node host browser proxy, not through a fake desktop browser inside every pod.

Supported OpenClaw Pattern Shared Browser Infrastructure No Desktop Browser Required In Pod

What Changed

  • The web researcher agent was pointed at the node-backed browser path instead of the local host browser path.
  • The Fedora VM became the real browser node host.
  • The node host was moved onto a clean OpenClaw home so it stopped inheriting old personal browser state.
  • The VM node host was upgraded to current OpenClaw and switched to headless Chromium server settings.

System Context

The pod remains the reasoning and gateway layer. The VM supplies the actual browser runtime through a paired node host.

Request Flow

The browser tool no longer depends on a local desktop browser in the pod. The gateway delegates browser execution to the connected node host.

Configuration That Made It Work

Agent Side

  • The web researcher agent was configured to prefer the node-backed browser route instead of the local host browser route.
  • The browser tool is enabled in the agent's OpenClaw config.
  • The agent remains in OpenShift and continues to use Codex as its reasoning model.
  • The gateway sees the node host as paired and connected with browser capability.

VM Side

  • The Fedora VM runs a dedicated systemd unit for the node host.
  • The node host now uses a clean OpenClaw home, separate from the user's older local OpenClaw setup.
  • The managed browser profile is openclaw.
  • Chromium is launched with server-safe settings: headless and noSandbox.
  • The VM node host was upgraded so its browser proxy behavior matches the newer OpenClaw gateway.

Why Earlier Attempts Failed

  • The pod originally tried to use the desktop-style host browser path, which is wrong for this containerized deployment.
  • The VM had stale OpenClaw state from a previous local setup, including an older gateway process and older browser assumptions.
  • The older node-host version was behind the gateway version and added more uncertainty around browser proxy behavior.
  • Chromium was initially launching headful, which failed on a VM context without an X display.
The final working state came from aligning the system with the intended OpenClaw pattern instead of forcing browser execution inside the pod.

Current Operational Model

This browser path is now suitable as the reference pattern for remote browser-capable agents in this environment:

  • Keep reasoning agents in OpenShift.
  • Run one or a small number of browser-capable node hosts on real machines or VMs.
  • Use managed browser profiles on those node hosts.
  • Route browser actions through the node host browser proxy instead of assuming every pod should carry its own desktop browser stack.
